## 1. 本轮确立的工作方法（比任何一条结论都重要）

### 1.1 核心信条：**先可信，再通用；内核自持，边界生成**

唯一不可妥协的是：**内核观测到的事实不被静默损坏、静默丢弃、静默假装存在。**
本项目全部重大缺陷都是这一条的反面：

| 缺陷 | 静默方式 |
|---|---|
| 13 个文件 / 5,092 行从未编译 | 无 CI，编译器看不到；`pub` 项 rustc 不报 dead_code |
| `ResponsibilityRuntime::run()` 85 行零调用 | 同上，直到发现它的字符串被 LTO 从 release 二进制里删掉 |
| 6 of 19 `impl Analyzer` 从未被构造 | 同上 |
| `CapabilityUse` 被 11 处模板要求、`graph/` 全目录零构造 | 没有任何机制断言"生产者存在" |
| `bin/replay` + 11 个 `server::web` 测试面向已停产的因果 schema | `#[ignore]` 无理由，22 个测试静默失效 |
| zstd 响应体被 `data.type=binary` 整条丢弃 | 无计数、无告警 |
| `.gitignore` 产物规则命中同名源码目录 | 三个 eBPF 程序不在版本控制里，全新 clone 不可构建 |
| `/health` 恒报 Healthy | `HealthState::new` 零调用者 |

### 1.2 方法论：**更深入，不是更大**

上一轮曾设计过 6 期 / 75–120 人日 / 若干新模块的方案（见 §9 的设计文档）。用户明确要求改为
**"更深入而非更大"**：先用不可辩驳的证据把现有系统钉死，再以"证明"为单位做删改。
**在没有验证脊梁之前，任何"我修好了"都只是断言**——而本仓库病史就是"断言与事实脱节"。

判断一个改动是否属于"更深入"的四个问题（用户原话，每次动手前自问）：

1. **该领域顶尖专业人士会做、而用户没要求的事是什么？**（例：先建 ground-truth oracle、量 FPR、注入静默降级、给解析器写分割不变性性质测试、写开销契约、做隐私脱敏工程、写威胁模型、内核矩阵 CI）
2. **他们会从哪些最原始材料开始，而不是已经消化过的内容？**（见 §1.3）
3. **他们会用什么具体方法与工具？**（差分测试 / 蜕变测试 / 性质测试 / 状态机模型测试 / 确定性 oracle / 变异测试 / 差分模糊 / 独立解码器交叉核验 / FPR+Wilson 区间）
4. **除了我和用户，什么能证明结果是对的？**（由强到弱：内核 verifier 与 `bpftool` 实际状态 → **agent 自己的独立记录**（OpenClaw sqlite / Claude Code JSONL）→ 独立解码器（`zstd -d`/`jq`/`openssl`）→ 确定性 → 第三方 clone 跑门禁 → 留出集统计 → 良性语料 FPR → 文献复现 → 变异测试）

### 1.3 原始材料优先级（不要用二手结论代替一手证据）

| 原始材料 | 为什么 |
|---|---|
| 内核 tracepoint 真实布局 `/sys/kernel/tracing/events/.../format`、vmlinux BTF | 每个 `ctx->args[N]` 的下标与类型由内核定义，不由我们猜 |
| **原始 wire 字节**（不是我们的 `HEX:`、也不是我们的 Event JSON） | 用 `zstd -d` / `gunzip` / `openssl` 独立判定"这到底是什么" |
| `/proc/<pid>/{status,stat,cgroup,cmdline,exe}`、`bpftool prog show` / `map dump` | 进程身份与挂载状态的第一手 |
| **agent 自己落盘的记录**：`~/.openclaw/agents/{main,probe}/agent/openclaw-agent.sqlite`、Claude Code 的 JSONL transcript | **唯一真正外部、与我们不同源的真相**（asserted vs observed 交叉验证）。已用它发现"工具定义被当成工具调用" |
| 上游源码：libbpf、BoringSSL/OpenSSL 头、Node TLS | 例：`libbpf/src/libbpf.c:14644` 的"首个 attach 失败即 return"就是这样定位的 |
| 规范原文：RFC 9110/9112/9658、OTel semconv YAML | 不读任何人的转述 |
| **DB 行本身（SQL）而非 reader 代码** | reader 会静默强制（`reader.rs:140` 未知 parse_state→`Complete`；`:185` 未知 action_type→`FileRead`） |
| git 历史（`git log -S`、blame） | 知道某行**为什么**存在 |
| 构建产物本身（`strings` / `bpftool prog dump xlated`） | 验证"编译器真的生成了什么" |

## 6. 必读陷阱（都实际踩过）

1. **cargo 产物在 `collector/build/` 不是 `target/`**（`.cargo/config.toml` 设 `target-dir="build"`）。`target/` 是 2026-08 旧码。
2. **eBPF 真实验证要 sudo**：`printf '%s\n' 1 | sudo -S -p '' <cmd>`（密码 `1`；凭据缓存不稳，每次显式喂）。
3. **本 harness 内进程的 `openat` 不被主机 eBPF tracepoint 观测**（`strace` 可见、无 PID namespace、`Seccomp:0`，但 `process` 与 `fileaccess` **同时漏掉**同一 marker）。⇒ **不要用"我自己起的进程"做 eBPF 采集验证**；要依赖已存在的长驻进程（OpenClaw gateway / agent 进程），或把待观测动作交给它们。任何"某 comm 没被捕获"的结论先排除这条。
4. **release 二进制里的 `strings` 可作死代码探针**：死掉的 `pub` 方法会被 LLVM/LTO 连同其字符串常量一起删掉（`run()` 就是这样被抓到的）。「加了日志却没打印」先查是否死代码。
5. **shell 脚本坑**：`cd X && sleep 600 &` 会把整个复合命令放进子 shell（`cd` 不生效）；`sudo -S` + 后台 + `wait` 会让工具输出被截断 ⇒ **一律写成 `.sh` 文件再执行**；`rm -rf "$D"` 而脚本自己在 `$D` 里会自删；`PATH=/nonexistent` 会顺带弄没 `sleep`/`echo`；`pkill -f 'mtagentlens'` 会匹配到我自己的 shell 命令行。
6. **不要用 index 切片改源码**：曾用 python 的区间切片删 Rust 方法，误删了相邻 4 个方法（7 个编译错误）。**用带断言的精确字符串锚点**。
7. **`make tls_capture` 是假成功**（匹配同名目录），要用 `make .output/bin/tls_capture`。
8. **`bpftools/.gitignore` 绝不能按程序名忽略**（见 §2.1 #1）。
9. **`trajectory_runtime_events.seq` 是 per-session 的**，跨 session 排序必须按 `created_at`。
10. **`/tmp` 会被清理**：重要抓包必须立刻入库，不要只留在 `/tmp`。
11. **chunk 数据与尾部 CRLF 可能在不同 `SSL_read`**：数据已到、CRLF 未到是"未完成"，
    不是畸形。P1 真机验证就栽在这里（`MissingChunkCrlf` 曾让整条响应判死）。
13. **时序断言在并行门禁下会 flake**：`security_tests.rs` 的比值断言曾让
    verify 偶发失败；用 best-of-N / 中位数，不要用均值或单次测量。
12. **clippy 计数依赖编译缓存**：`cargo clippy` 不会为 fresh crate 重放 warning，
    热缓存下会少报并让门禁静默通过。`verify.sh` 先 `touch` 所有 `.rs` 再计数。

    （2026-10-17 已重新抓取并入库；原始捕获仍在 `/tmp/p05/`，fixture 与 MANIFEST 在
    `collector/tests/fixtures/wire/`。）
