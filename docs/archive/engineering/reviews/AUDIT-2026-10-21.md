## 0. 一句话结论与最高杠杆改动

当前代码库的问题不是零散 bug，而是**四条主干契约同时失效**：(1) 阶段 2 判定不是阶段 1 状态的延续，而是用缺信号的图重算；(2) "证据充分性"不是图边/claim 的一等属性，导致意图级 provisional 边可以直达 Authoritative Critical；(3) 评测脚本各自复制业务逻辑，产出与运行时不一致的数字（FPR 置信区间恒为 0、claim coverage 单位错误、消融用过期融合公式）；(4) 采集层大量静默丢失（argv、限流、PID 表、零探针）没有任何计数契约。

**最高杠杆的五处改动**（做完即可让"新实验数字可信"这件事从不可能变为可能）：

1. `runtime.rs::finalize` 把 `correlate_batch` 结果灌回 `graph_builder.handle`，并把 phase-1 的 `content_threat`/`baseline_deviation` 写回字段（P0-06/07）。
2. 规则/claim/traceback 三层统一"只有 evidence_refs 非空或 Authoritative phase 的边才能升级为硬证据"（P0-09/10）。
3. 评测脚本改为"重算 == 持久化值"自校验：FPR 用 benign 1/0、claim coverage 换成真分母、消融移植 `fusion.rs`、GT 枚举排除 `_reviewers`（P0-01..05）。
4. eBPF 三个静默洞补齐：argv 原始拷贝、PID 表 tombstone/后退移位、限流计入 dropped；零探针必须非零退出（P0-15..18）。
5. 持久化层所有 run 级主键加 `run_id`，服务端统一 run 解析策略（单 run 接受/精确匹配/409）（P0-24/25）。

## 1. 架构层面根因（10 个主题）

### R1. 双阶段判定不是同一状态机的两次快照，而是"重算 + 丢信号"

**根因**：`finalize()` 把阶段 2 当作一次独立的、更"权威"的计算，但它拿到的是**未被阶段 2 证据更新过的图**，且阶段 1 的语义信号（DeBERTa、baseline deviation）从未写回结构体字段。阶段 1 与阶段 2 因此**按构造必然分歧**，而对外只发布阶段 2。

**集中体现**：
- `collector/src/responsibility/runtime/runtime.rs:1702-1743`（correlate_batch 只持久化，不 `graph_builder.handle`；`let _frozen` 丢弃）
- `runtime.rs:152-154, 946-1050, 1772-1773`（`last_content_threat`/`last_baseline_deviation` 永不赋值）
- `runtime.rs:948`（per-agent 打分绑定到 HashMap 迭代出的任意 agent）
- `collector/src/responsibility/classification/engine.rs:435-495`（authoritative 结果把 CUSUM/DeBERTa/trigger 全部硬编码为 0）
- `collector/src/responsibility/replay/executor.rs:213-219`（replay 把 `intents.len()` 当 repetition_count，与 live 不同）
- `collector/src/responsibility/claims/alert_builder.rs:284-285`（final verdict 分支丢弃 pattern_verdicts）

**为什么是根因**：这不是"某处忘了赋值"，而是缺少一个**单一的 AuthoritativeRunState**（包含图 delta、证据、信号、阶段 1 观测），阶段 2 只做"增量合并 + 裁决"。当前每个字段都靠散落的局部变量传递，任何新增信号都必然再次丢失。修复必须引入该状态对象，而不是逐条补赋值——否则下一条信号仍会掉。

**关联 finding**：phase-2 batch evidence；phase-2 None signals；任意 agent 打分；instrumentation 归零；pattern_verdicts 为空；replay 参数错位；evaluation summary 伪造计数（部分）。

### R2. "证据充分性"不是图边/claim 的一等属性

**根因**：`PolicyBoundaryCrossing` 同时承载"意图命名了敏感路径"（confidence 0.60、`evidence_refs=[]`）和"OS 观测到越界"（有证据）两种语义。规则引擎扫描 `all_edges()` 时不看 phase/confidence/evidence；claim builder 原样复制 `evidence_refs`；traceback 在无证据时回退到"第一条 PBC 边"。于是**意图即判决**，且归因可以指向别的 agent。

**集中体现**：
- `collector/src/responsibility/classification/rule_engine.rs:58-108`（无 phase/confidence 过滤）
- `collector/src/responsibility/graph/graph_builder.rs:1005-1074`（`handle_intent_pbc` 造 0.60 空证据边）、`:136-175`（provisional 边从不删除）
- `collector/src/responsibility/claims/claim_builder.rs:208`（原样复制 evidence_refs）、`:384-411`（0.85 → Confirmed/Critical）
- `collector/src/responsibility/claims/traceback.rs:193-232`（agent 匹配 +2 高于证据重叠 +1，且 `pbc_edges.first()` 兜底）
- `collector/src/responsibility/classification/final_decision.rs:126-135`（HardViolation → Unsafe/Critical/Authoritative）

**为什么是根因**：项目核心卖点是"责任归属要有证据链"，但数据模型把证据放在可选数组里、把阶段放在一个只读不用的枚举里。FPR 污染、claim 精度虚高、traceback 错配都是同一缺陷的不同投影。修复需要**边级不变量**：`phase == Authoritative ⟺ evidence_refs 非空 ⟹ 可参与硬规则`。

**关联 finding**：intent-only PBC → HardViolation；空证据 claim → Confirmed/Critical；traceback 任选边；UnauthorizedCapabilityUse 不可达（因为 ICA/PBC 目标域永不重合）；graph refinements 引用不存在的 id。

### R3. ID / 时间 / 身份域没有类型与作用域约束

**根因**：`EdgeId`、`EvidenceId`、`AgentId`、`ProcessId` 都是 String newtype，可以互相 `From`；`ProcessId` 含 `start_time_ns`，但 HTTP/TLS 事件该字段恒为 0；provisional agent id 在 refine 前就被重命名抹除；HashMap 迭代顺序决定 subject/cache key；`account_uuid` 被当会话 id；subagent boundary 在遍历中途生成最终 id。

**集中体现**：
- `graph/graph_builder.rs:1159-1164`（`EdgeId::from(evidence_id)`）、`:1093-1107`（provisional id 已被 remap 抹除）、`:238-263`
- `runtime/runtime.rs:421-429`（`start_time_ns` 取 0）、`:1132-1166`（HashMap 顺序入 key）
- `identity/union_find.rs:425-456`（boundary id 中途生成）、`:603`（最终 id 最后才生成）
- `runtime/provenance_tracker.rs:368-377`（account_uuid 兜底）
- `persistence/reader.rs:67-77`（phase 时间戳归零）、`framework/core/events.rs:64-93`（ms/ns 双表示）

**为什么是根因**：没有"ID 只能在其域内流动"的类型约束，也没有"确定性顺序"的全局约定；这类错误不会崩溃，只会让审计数据在需要精确归因时不可用。

**关联 finding**：graph refinements；ProcessId 键错导致跨 agent 污染；subagent boundary 幽灵节点；account_uuid 合并多 agent；cache key 不稳定；phase 时间戳；Event JSON 单位。

### R4. 缓存 / 去重 / 限流的键与失效语义错误

**根因**：四处机制都用了**与内容无关的键**并配以**永不过期的存储**：Observer L1 key 只含类型集合（不含 score/rule/evidence）；intent 去重只用内容哈希且全局不重置；`CacheTTL` 被模型返回但被硬编码 Task 覆盖、cache 本身无过期；文件 open 限流在去重前计数且丢弃不记账。结果是"命中率不可复现、合法重复被吞、失败被当判决、证据被截断"。

**集中体现**：
- `observer/types.rs:269-287`、`runtime/runtime.rs:1132-1166,1304-1329`、`observer/cache.rs:63-81`
- `runtime/buffer.rs:45,80-83,151-163`（全局签名集合）
- `runtime/provenance_tracker.rs:76-79` + `provenance/span_store.rs:85-114`（保留最旧 64、重复入库）
- `bpftools/process/process.c:200-240`（限流先于去重）

**为什么是根因**：这四处共享同一个思维错误——"形状相同即语义相同"。在安全判定里，形状相同恰恰是最不能省的区分维度（同样的 6 个维度分可以是完全不同的行为）。

**关联 finding**：cache key 丢证据；TTL 未实现；失败结果入缓存并被重放为 verdict；强制触发被缓存中和；intent 重复被吞；span 保留最旧；限流削峰。

### R6. 采集层静默丢失，无 capture-health 契约

**根因**：eBPF 侧只在 ringbuf reserve 失败时 `inc_dropped()`；entry map 更新失败、return-probe 状态 miss、限流、噪声过滤、PID 表失效、零探针启动**全部不计**。userspace 又把读错误变成干净 EOF、把子进程异常退出只打 debug 日志。于是"零 dropped"完全不能证明采集完整。

**集中体现**：
- `bpftools/process/process.bpf.c:196`（argv）、`:47-81`（噪声过滤）、`:265`（exit_code）
- `bpftools/include/process_filter.h:106`（墓碑删除）
- `bpftools/process/process.c:236-275`（限流）
- `bpftools/tls_capture/tls_capture.c:408-435,700-708`（零探针退出 0）
- `bpftools/tls_capture/tls_capture.bpf.c:104-125,147,209-234,253-254,323-345`（状态 miss 与 256KiB 预留）
- `collector/src/framework/runners/common.rs:298-306`（读错误 → EOF）

**为什么是根因**：论文的 completeness/FPR/TPR 全部以"这条 run 完整"为前提，而系统没有任何机制能证明这一点。必须在 eBPF 与 collector 之间定义**每一类丢失都有独立计数器**的契约。

**关联 finding**：argv、PID 表、限流、零探针、256KiB、entry miss、噪声过滤、dirfd、stdiocap fd、exit code、读错误 EOF。

### R7. 流式三态未建模：完整 / 截断 / 中断

**根因**：管线只有 `partial` 一个布尔，且只覆盖响应读方向。请求写方向的截断（HTTPParser 无 Content-Length 校验、record 链缺 ConnectionBuffer）、ringbuf 丢字节（`truncated/bytes_lost` 不进 SSE/HTTP 事件）、关闭时的流丢弃（goroutine 生成器尾部不执行）都没有状态表达。三种截然不同的语义被压成"一个事件"。

**集中体现**：
- `framework/analyzers/http_parser.rs:81-164,223-246`
- `framework/analyzers/connection_buffer.rs:5-12` + `collector/src/main.rs:1373-1409`（record 链未注册）
- `framework/analyzers/sse_processor.rs:669-715`（只查 partial）
- `framework/runners/common.rs:184,310-325`（无 kill_on_drop）
- `runtime/runtime.rs:2237-2242`（shutdown 直接 break）
- `framework/runners/outofband.rs:204-210`（boot ns 未归一化）

**为什么是根因**：检测器在"不完整输入"上运行却不自知，TPR 的分母因此不可解释。必须引入 `Completeness { Complete, Truncated{lost}, Interrupted }` 并让每个阶段继承。

**关联 finding**：HTTPParser 截断、ConnectionBuffer 缺失、lossy 被 finalize、读错误 EOF、shutdown 丢流/孤儿子进程、outofband 时钟域。

### R8. 持久化与服务层缺"run 作用域"

**根因**：schema 的主键设计把 `pid+start_time`、`agent_id`、`boundary_id` 当全局唯一，而代码自己承认"复用 `-o` 会让 DB 累积多个 run"。服务端随后用 `list_runs().first()`（最新 run）填补任何解析失败。多 run DB 从"支持的状态"变成"静默串数据的状态"。

**集中体现**：
- `persistence/schema.rs:163,268,388` + `writer.rs:570,911,1021`（无 run_id 键、REPLACE 抢行）
- `server/web.rs:892-945,1286-1337`（无作用域查询/最新 run 兜底）
- `persistence/reader.rs:362-372`（get_alerts 无 phase 过滤）
- `schema.rs:697-711`（v3 迁移无回填）
- `writer.rs:376-384`（batch 定时器被重臂）
- `export/genai.rs:124-138` + `main.rs:800`（全库导出、0644、非原子）

**为什么是根因**：run 是产品的第一维度（一次采集 = 一个证据单元），但 schema 与查询都没有把它当第一维度。修单点（如给 evidence 加过滤）会反复出现，必须统一 run 解析策略并下沉到 schema。

**关联 finding**：最新 run 端点、summary 无作用域、replay 全量载入、run 键冲突、run metadata 空、phase 解析丢失、v3 无回填、导出越界。

## 2. 按优先级排序的修复清单

- **P0**：会让新实验数字错误、让产品对真实运行给出错误安全判定、或崩溃/阻断工作流。

## 附录 A：建议新增的契约测试（防止回归）

1. **Phase-2 等价性**：同一 run 的 phase1 观测与 phase2 裁决在无新证据时必须一致（除显式 review 规则）。
2. **证据不变量**：`Claim.state == Confirmed ⟹ evidence_refs 非空`；`HardViolation ⟹ 存在 observed action`。
3. **确定性**：同一输入两次运行，`per_agent_scores`、claim 顺序、cache key 相同。
4. **run 隔离**：双 run DB 上所有端点要么返回请求 run 的数据，要么 409。
5. **采集健康**：每一类丢弃（ring、state、filter、rate、probe-miss）都有非零计数可达路径的单测。
6. **流式三态**：完整/截断/中断三种输入分别产生可区分的事件或诊断。
7. **评测自校验**：FPR/coverage/消融三项在合成数据上必须等于手算值。
8. **GT 枚举**：`ground_truth.rglob("*.json")` 必须只返回 `schema==v4` 且排除 `_*`。
9. **Observer 安全**：含分隔符/citation 伪造/空 JSON 的响应不得产生 actionable verdict。
10. **文档派生**：路由表、CLI 表、规则数、内核下限由代码/常量生成，CI 断言无漂移。
