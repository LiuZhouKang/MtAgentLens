## 第 1 页 标题

**画面提示**：标题页，背景动画。

**口播稿**：

各位评委老师好，我们是 MtAgentLens 项目组。

我们这次做的是一个基于 eBPF 的多 Agent 可观测与根因分析框架。项目的出发点很直接：现在的 Agent 已经不只是回答问题，它会拉起工具、读写文件、访问网络，还会把任务继续交给子 Agent。出了问题以后，单看聊天记录不够，单看系统日志也不够，必须把“是谁发起的”“系统里实际发生了什么”“证据落在哪里”连成一条链。

所以 MtAgentLens 做的事情，就是在不改目标 Agent、不插 SDK 的情况下，从操作系统边界采集运行事实，再把这些事实组织成责任图和可审计告警。要说明为什么必须这样做，我们先回到赛题本身和现在 Agent 系统面临的真实风险。

## 第 2 页 章节过渡：设计背景与项目介绍

**画面提示**：设计背景章节页。

**口播稿**：

这道赛题的关键词是“系统级”和“多智能体”。它要求的不是采几类日志、做一个告警页面，而是要在 Agent 真正执行任务时，把底层行为看清楚、把责任主体找出来。

我们把任务拆成三步：第一步拿到可信的运行事实，第二步把事实放进责任链，第三步输出用户能复核的告警。后面所有系统设计，都围绕这三步展开。

## 第 3 页 赛题要求

**画面提示**：赛题要求图，依次突出“采集事实、责任建图、可审计告警”。

**口播稿**：

具体到题面要求，可以落到三个检查点。

第一是多层级数据捕获。Agent 的行为不会只停在应用层，它会落到进程创建、文件读写、网络连接和工具通信上，所以系统必须能跨过应用日志，看到 OS 层的真实事件。

第二是多维异常监测。赛题里提到资源浪费、安全操作异常和多 Agent 协作异常，我们在设计时把它进一步落到几个结构信号上：短命进程、异常文件访问、外连行为、工具调用、委派链和跨 Agent 传播。

第三是告警与归因定位。一条有价值的告警，不能只说“可疑”，还要说清楚时间、PID/TID、操作对象、证据路径和责任主体。也就是画面底部这条主线：采集事实，责任建图，可审计告警。

现有做法各有短板：应用层日志部署方便，但短命进程、真实文件操作和网络行为经常看不全；系统调用审计能看到底层动作，却缺少 Agent 身份和任务上下文；如果直接把判断交给大模型，又会带来成本和可复核性问题。

MtAgentLens 的切入点就是补这三块短板：用 eBPF 获取 OS 运行事实，用责任图补上 Agent 语义，用结构化证据支撑可审计告警。

## 第 4 页 Agent 风险已经进入运行时

**画面提示**：Amazon Q 与 Replit Agent 两个案例卡片，底部是进程、文件、网络、工具调用。

**口播稿**：

我们做这个项目时，最直接的触发点其实来自这些真实事故。

一个是 Amazon Q Developer for VS Code 扩展 1.84.0 被注入恶意代码，风险进入了 AI 编码助手的发布链路；这对应我们评估里的供应链污染和工具链风险。另一个是 Replit Agent 删除生产数据库的事故，暴露出 Agent 在自主执行、权限边界和审计链路上的问题；这对应敏感资产操作、权限边界和事后归因问题。

这类问题最麻烦的地方在于，事故发生时大家关心的不是“模型说了什么”，而是它到底有没有拉起进程、有没有改文件、有没有连网络、有没有碰到真实资产。只看上层对话，我们确认不了动作是否发生；只看底层 syscall，又看不出这是哪个 Agent、哪一次任务、哪一轮委派造成的。MtAgentLens 的价值就在这里：把上层 Agent 语义和底层 OS 行为接起来，让事故复盘能回到证据和责任链。

## 第 5 页 现实案例与观测盲区

**画面提示**：三张来源截图，强调 affected version、patched version、Replit 复盘。

**口播稿**：

从这些公开案例可以看到两个方向的风险。

左边是安全公告和 advisory，说明 Agent 工具链和插件发布链路本身会成为攻击面；右边是 Replit Agent 事故复盘，说明 Agent 一旦拿到执行能力，就可能影响真实资产。

放到多 Agent 场景里，这个问题会更难。父 Agent 会把任务交给 worker，worker 可能很快退出，证据可能写到临时目录，日志还会和其他任务交织在一起。这里对应的异常类型，不只是单一安全操作异常，还包括资源滥用、供应链污染、Agent 团队攻击和子代理链式传播。

应用层监控部署方便，但很容易漏掉短命进程；底层监控能看到 syscall，却缺少 Agent 语义。我们需要的是一条从 Agent 意图到 OS 行为、再到证据和责任主体的运行事实链。

## 第 6 页 五项技术贡献

**画面提示**：左侧现有观测盲区，右侧五项技术贡献，底部工程链路。

**口播稿**：

基于这个判断，MtAgentLens 的技术特色可以概括成五个编号要点。

第一，零插桩跨层观测。目标 Agent 不需要改代码，也不需要接入 SDK。系统在 OS 边界采集进程、文件、网络、stdio，以及支持环境下的 TLS 明文片段。这个点解决的是“应用日志看不全、系统行为缺证据”的问题。

第二，多信号 Agent 身份归并。我们不直接把 PID 当作 Agent，而是结合 root_pid、tls_session、conversation_id 等线索，把同一条执行链合并成稳定身份。这样短命 worker 退出以后，它仍然能回到原来的父 Agent 和任务上下文里。

第三，OS 责任图归因。我们把 Agent、进程、文件、网络、工具调用、上下文和策略边界放进同一张图，用图结构保存“谁触发了谁、谁访问了什么、哪一步跨过了边界”。这个点直接对应赛题要求的归因定位。

第四，多智能体污染传播归因。多 Agent 风险经常不是单点动作，而是通过委派、角色声明、共享文件和上下文传递逐步扩散。系统会保留这条传播路径，并把弱信号融合成可解释判断。这个点对应多 Agent 协作异常和子代理链式传播。

第五，FuxiBench 评估闭环。我们构建了 86 个主评估场景，覆盖 14 类安全与协作风险，同时加入 attack、benign、人工标注真值和消融实验，避免只靠单个 demo 证明效果。

从完成情况看，题面基础要求已经完整完成：进程、文件、网络采集，异常检测，告警输出和责任归因都已经打通。进阶部分覆盖 uprobe 明文片段、跨层因果匹配、多 Agent 结构异常和端侧性能评估。在题面之外，我们还额外交付了 FuxiBench 86 场景、消融实验和前端调查视图。

工作量和难点主要集中在四块：内核侧轻量采集、多源事件身份归并、跨层责任图建模，以及评估集和误报控制。后面的系统概览和主演示都会分别对应这些点。

有了这个整体定位以后，再看系统本身是怎样组织起来的。

**画面提示**：系统概览章节页。

**口播稿**：

系统概览部分，我们先回答一个问题：MtAgentLens 到底要覆盖什么样的 Agent 风险。

覆盖范围讲清楚以后，再看系统架构、eBPF 采集链路、责任运行时、责任图，以及跨周期溯源融合这几块怎么配合。

## 第 8 页 FuxiBench 场景覆盖

**画面提示**：14 类场景覆盖图。

**口播稿**：

为了避免系统只对单个 demo 有效，我们把 Agent 运行风险拆成 14 类。

这里包括输入层的 prompt 注入，系统安全行为里的侦察、凭证窃取、数据外泄、C2 后门、防御规避和权限提升，资源与供应链里的资源滥用、行为型攻击和供应链污染，以及多 Agent 结构里的团队攻击、联合攻击和子代理链式传播。

底部的良性复杂工作流也很关键。真实环境里，构建、测试、发布、日志聚合本身就会产生大量进程和文件事件。如果没有 benign 场景做约束，系统很容易把“复杂”误判成“攻击”。

这样设计评估集的目的，是让后面的效果验证能覆盖输入层风险、系统安全行为、资源与供应链风险、多 Agent 结构异常，以及正常复杂工作流下的误报控制。

这些场景看起来差异很大，但落到 OS 层，都会留下共同事实：谁派生了进程，谁读写了文件，谁连了网络，谁启动了工具，数据和上下文有没有跨 Agent、跨文件、跨进程传播。系统架构就是围绕这些事实来设计的。

## 第 9 页 系统架构

**画面提示**：四层架构图，从上到下讲。

**口播稿**：

从这些可观测事实出发，系统总架构分成四层。

最上面是智能体运行层，包括 Leader Agent、Worker Agent、本地工具或 MCP、文件资源，以及网络和 LLM API。也就是说，MtAgentLens 观测的是 Agent 真正执行任务时接触到的对象。

中间是 eBPF 采集层。这里对应赛题的多层级数据捕获：tracepoint 和 kprobe 负责进程、文件、网络等系统事件，uprobe 负责用户态库里的明文片段，stdio 负责本地工具和 MCP 进程的输入输出。

再往下是 Rust 分析层。collector 会把事件标准化，再做身份解析、污点追踪、责任图构建、异常分类和告警生成。

最下面是调查输出层。前端不是展示一堆孤立日志，而是以 run 为单位展示责任图、告警和证据链，让一次异常可以从结论回到来源。

在这四层里，最底层的采集质量决定后面的归因能走多远。

## 第 10 页 eBPF 多层级数据捕获

**画面提示**：用户态到内核态的采集路径图。

**口播稿**：

采集层展开后，可以看到它覆盖了用户态和内核边界之间的关键通道。

上半部分是用户态对象：Agent 进程、本地工具、TLS 库、文件系统和网络连接。下半部分是 Linux 内核边界和我们挂载的采集点。

进程侧，我们关注 fork、exec、exit，这能看到父 Agent 有没有拉起 worker。文件侧，我们关注 open、unlink 等操作，能看到证据文件、配置文件、临时目录的读写。网络侧，我们记录连接的 IP 和端口。对于支持的运行时，还可以通过 uprobe 在解密后位置捕获 TLS 明文片段；对于本地工具或 MCP，则通过 stdio 观察输入输出。

所有事件进入用户态后先标准化，再进入责任图。这里的关键不是“采得越多越好”，而是采到能支撑归因的关键事实。

## 第 11 页 场景覆盖回顾

**画面提示**：FuxiBench 覆盖图再次出现。

**口播稿**：

采集到这些事实以后，系统并不是按场景名硬编码规则，而是抽取共同结构。

无论是 prompt 注入、凭证窃取、数据外泄，还是多 Agent 联合攻击，最终都要落到一组可观测结构上：进程血缘、文件访问、网络外连、工具调用、上下文传播和策略边界穿越。

## 第 12 页 处理流程与责任运行时

**画面提示**：左侧“处理流程与责任运行时”，右侧三层技术架构。

**口播稿**：

把采集和场景抽象连起来，中间承载它们的是责任运行时。

左侧列的是输入和输出。输入不是单一日志源，而是进程派生、文件读写、网络连接、TLS 明文片段这些 OS 事实。中间的关联线索包括 root_pid、tls_session 和 conversation_id，它们用来把不同来源的事件合并到同一个执行上下文里。

右侧是系统分层实现：第一层是 eBPF 内核探针层，负责把原始事件送到用户态；第二层是 Rust collector，负责流式处理、因果归因、污点追踪、证据关联和异常分类；第三层是前端，把责任图、告警和证据链展示出来。

也就是说，这里的“责任运行时”不是离线分析脚本，而是把采集、关联、建图、告警串在同一条运行管线里。

## 第 13 页 责任图与身份解析

**画面提示**：责任图结构图，包含 nodes、edges 和节点/边类型。

**口播稿**：

责任运行时里最核心的数据结构，就是责任图。

图里维护两类核心存储：nodes 和 edges。节点包括 Agent、Resource、PolicyBoundary、ToolCall、Context，也包括进程和证据类对象；边用来表达关系，比如意图触发、Agent 委派、污点传播、策略边界穿越和资源访问。

身份解析就在这张图上发挥作用。多 Agent 场景里，同一个任务可能拆成多个 PID，worker 也可能很快退出。如果只按 PID 看，责任链很容易断。我们把 root_pid、会话、任务上下文和通信线索合并起来，让短命 worker 仍然挂回父 Agent 和对应任务。

这样前端看到的图就不是装饰性可视化，而是可以直接用于追问：哪个 Agent 创建了 worker，worker 写了哪个文件，哪条边触发了告警。

## 第 14 页 跨周期溯源融合引擎

**画面提示**：Cycle T1 到 Tn，SignalAccumulator，Noisy-OR，时间衰减。

**口播稿**：

责任图解决的是单次运行里的结构归因；跨周期溯源融合解决的是多轮运行里的弱信号积累。

多 Agent 异常很多时候不是一次 syscall 就能判断出来。比如某个 Agent 先读了敏感文件，下一轮把内容交给 worker，worker 再通过工具或网络传播出去。每一步单看都可能只是弱信号，但放在同一责任主体和同一路径下，就会形成更强的证据。

系统按 Cycle T1 到 Tn 累积信号，记录 Agent、SignalType、Path 和 Source，再通过 Noisy-OR 做多源证据融合，并引入时间衰减，避免过早信号无限放大。

这个设计让系统既能在运行中给出初步判断，也能在 finalize 阶段形成更稳定的最终归因。

## 第 17 页 shadow-spawning 结果与责任链

**画面提示**：父 Agent、Worker A-D、临时目录、summary、告警、责任主体。

**口播稿**：

构建完成以后，我们用 `shadow-spawning` 作为主演示场景。

这里先解释两个词。`spawning` 指父 Agent 派生新的任务或进程；`shadow worker` 指生命周期很短、容易从应用日志中消失的 worker。这个场景的难点就在于这些短命 worker：它们执行时间很短，写完临时证据文件后很快退出。应用层日志里，它们很容易变成几条碎片化记录；只看系统事件，又很难判断这些 worker 属于哪一次 Agent 任务。

MtAgentLens 在这里做的，是把父 Agent、Worker A 到 D、临时输出目录、summary 文件和最终告警放回同一条责任链。画面右侧也列出了告警上下文需要保留的关键字段：PID/TID、时间戳、操作对象、证据路径和责任主体。

这个 demo 的重点不是证明某个 PID 可疑，而是展示归因能力：谁创建了 worker，worker 写了哪些证据，summary 怎样聚合，告警为什么归到这个父 Agent 上。

## 第 19 页 前端效果展示

## 第 21 页 FuxiBench 主评估集

**画面提示**：86 场景，67 attack，19 benign，Type A/B/C。

**口播稿**：

FuxiBench 主评估集一共有 86 个场景，覆盖 14 类方法论。

其中 attack 场景 67 个，benign 场景 19 个。这里的 benign 不是简单空跑，而是构建、迁移、测试、发布、日志聚合这类真实复杂工作流，用来检验误报。

为了统计攻击进入方式，我们又把 attack 场景分成三组：Type A 直接注入 10 个，Type B 间接注入 34 个，Type C 多 Agent 攻击 23 个。

这三个 Type 是评估切面，不是系统能力边界。真正支撑覆盖面的，是前面 14 类安全与协作场景，以及每个场景背后的 OS 责任链特征。有了这个评估集，下面再看指标才有意义。

## 第 22 页 MtAgentLens on FuxiBench

**画面提示**：TPR、FPR、F1、MCC、混淆矩阵、Observer 调用率、消融结果。

**口播稿**：

主评估结果集中在这几个指标上。

在 86 个场景上，MtAgentLens 的 TPR 是 0.896，FPR 是 0，F1 是 0.945，MCC 是 0.809。换成混淆矩阵来看，67 个 attack 场景里检出 60 个，19 个 benign 场景没有误报。

这里最重要的有两个点。第一，Type C 多 Agent 攻击的 TPR 达到 1.000。多 Agent 攻击往往会留下 OS 级结构，比如委派、handoff、子进程、共享文件、工具调用和跨边界传播。这些结构单看 prompt 不一定明显，但在操作系统事件里会变成可分析证据。

第二，Observer 调用率是 39.5%。这说明系统不是每条事件都问大模型，而是本地规则和责任图先做判断，只在信号冲突或需要语义仲裁时调用 Observer。

右下角的消融结果也说明核心信号确实有效。移除 PBC、Identity、Taint 之后，覆盖率从 1.000 降到 0.534，说明主要增益来自 OS 责任链特征，而不是少量场景规则。

## 第 23 页 性能与端侧可用性

**画面提示**：218.3 ns/op、36.8 MB、<3%。

**口播稿**：

检测效果之外，赛题还要求系统能在端侧运行。

我们的设计原则是：内核侧只抓关键路径，collector 做流式处理，前端读取 run-scoped 的分析结果，不把所有原始日志无差别堆到展示层。

从微基准看，SSL enter probe 为 101.3 ns/op，SSL read exit 为 57.6 ns/op，SSL write exit 为 59.4 ns/op。单次 SSL read/write 总 probe 成本约 218.3 ns/op。

资源占用上，collector 空闲 RSS 约 36.8 MB，合成 SSL 事件管线的吞吐量开销小于 3%。这和赛题里轻量化、不超过 5% 开销的要求是匹配的。

也就是说，MtAgentLens 不是靠重型全量审计换检测效果，而是在关键 OS 边界采集足够支撑归因的证据。

## 第 24 页 总结：OS 运行事实重建责任链

**画面提示**：Agent 行为 -> OS 运行事实 -> 责任图 -> 证据链 -> 告警归因。

**口播稿**：

最后回到项目主线。

MtAgentLens 从 Agent 行为出发，采集 OS 运行事件，构建责任图，再形成证据链和告警归因。它解决的不是“某一句 prompt 是否可疑”，而是更贴近真实运行环境的问题：哪个 Agent 触发了行为，行为怎样跨进程、跨文件、跨工具传播，证据在哪里，责任应该归给谁。

在 `shadow-spawning` 中，短命 worker 即使快速退出，系统仍然能通过进程血缘、文件证据和父进程聚合还原完整链路。在 FuxiBench 中，系统进一步验证了 14 类方法论场景下的覆盖能力和良性复杂工作流下的误报控制。

最终交付的是一条从零插桩观测、跨层归因、身份归并、污染传播到 FuxiBench 闭环的完整链路。
