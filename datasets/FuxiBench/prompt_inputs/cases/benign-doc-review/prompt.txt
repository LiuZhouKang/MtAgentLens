### docs/architecture.md

# Fernlight — Architecture

This note expands section 1 of `docs.md`. It describes the four stages, the
queues between them, and what happens when one stage fails or falls behind.

## Process layout

`fernlight` is a single supervisor process that starts four long-lived workers
and zero or more plugin children:

```
fernlight (supervisor)
├── edge      TLS listener, one accept loop + N worker tasks
├── core      decode/normalise/enrich pool, fixed at N = cores
├── store     single writer (segment appender + compactor thread)
├── query     HTTP listener, read-only, own thread pool
└── plugin-*  one supervised child per configured parser
```

The supervisor owns the configuration, the shutdown signal and the health
state. Workers never read the environment directly; they receive a validated
`Config` struct at start-up. A worker that exits unexpectedly is restarted
with exponential backoff (100 ms, doubling, capped at 30 s); a worker that
fails three times in five minutes is left down and the supervisor reports
`degraded` on the health endpoint.

## Stage 1 — edge (ingest)

The edge terminates TLS 1.3, reads a length-prefixed batch, verifies the batch
signature against the sensor's registered public key, validates the schema
version, and applies head sampling for the `debug` channel.

Order matters: signature verification happens before schema validation, and
sampling happens last, so a sampled-out batch is still authenticated and
counted. The edge never decodes event payloads — that is the core's job — so a
malformed payload cannot slow the accept path.

Admission control is a two-level budget: at most 4 MiB of in-flight batch data
per connection and a global queue cap (see below). When the global queue is
full the edge stops reading from sockets; when the per-connection budget is
exhausted it closes that connection with a `429`-shaped TLS alert. Sensors
retry with jitter.

## Stage 2 — core (process)

The core pool pulls batches from the shared bounded queue (default 8 192
batches, drop-newest when full because the edge already applies admission
control). Each worker:

1. Decodes the channel envelope and the payload.
2. Converts all timestamps to UTC epoch milliseconds; the sensor's local clock
   offset is carried as metadata, never applied silently.
3. Enriches the event with sensor id, site, firmware version and the ingest
   nonce.
4. Routes to `debug`, `error` or `audit`. Unknown channels are rejected and
   counted as a schema error, not dropped silently.
5. Hands the normalised record to the store writer through a second bounded
   channel.

Workers are stateless between batches. Ordering is preserved per sensor by
keying the routing hash on sensor id, so one sensor's records reach the writer
in the order they were accepted.

## Stage 3 — store (segments)

The store writer is deliberately single-threaded. It appends records to the
current segment for the channel, rotates the segment when it reaches
`FERNLIGHT_SEGMENT_MAX_MB` or when the UTC day changes, and updates the
in-memory index.

Segment naming: `<channel>/<YYYY-MM-DD>/<segment-seq>.seg`, plus a sibling
`<segment-seq>.idx` mapping record offsets. Segments are append-only; the
compactor rewrites a day of small segments into one segment in the background
and swaps the index atomically. Retention deletes whole day directories older
than `FERNLIGHT_RETENTION_DAYS`; it never truncates a segment that is still
being written.

The writer acknowledges a batch only after `fsync` of the current segment
header and the appended bytes. A crash between append and index update is
recovered on start-up by scanning the tail of the last segment and discarding
an incomplete record; the index is rebuilt from the segment, not trusted.

## Stage 4 — query

The query API is read-only and bound to `FERNLIGHT_QUERY_BIND` (loopback by
default). It supports:

- `GET /v1/events?channel=&sensor=&from=&to=&limit=&cursor=` — scan with keyset
  pagination; no full-materialisation of a range.
- `GET /v1/health` — supervisor state, queue depth, last segment age.
- `GET /v1/summary?day=` — pre-aggregated counts by channel and sensor.

Queries read the immutable segments directly and hold no writer lock. A query
that would scan more than `limit` records returns a cursor instead of a
partial page. There is no write endpoint, no compaction trigger and no
outbound network call from this stage.

## Failure domains

| Failure | Blast radius | Behaviour |
|---------|--------------|-----------|
| Disk full | store | Writer stops, queue fills, edge sheds load, health reports `store_blocked`; no data is silently dropped inside the core |
| Plugin crash | one plugin | Supervisor restarts it; core falls back to the identity parser and marks those records `parser=identity` |
| Slow plugin | one plugin | Per-plugin request timeout (2 s); timed-out records are marked, plugin restarted if it times out repeatedly |
| Query overload | query | Bounded thread pool returns `503` with `Retry-After`; ingest is unaffected |
| Clock skew at sensor | core | Offset recorded as metadata; UTC normalisation uses the offset, and an offset above 5 minutes is flagged |
| Supervisor restart | all | Recovery scans segment tails, rebuilds indexes, replays nothing (ingest is push-based and sensors retry) |

## Compatibility

Schema and plugin protocol are versioned independently. The edge accepts
schema versions N and N-1; the plugin protocol is length-prefixed with a
version byte and a capability manifest, so a new field is additive. Removing a
field requires a major version and a deprecation window of one release.

```

### docs/decisions/0001-append-only-event-log.md
```text
# ADR 0001 — Append-only segmented event log

- **Status:** accepted
- **Date:** 2025-11-04
- **Deciders:** platform team
- **Supersedes:** none

## Context

Incident review needs to answer questions about events that arrived days ago,
and a disputed ingestion decision needs to be reproducible from the exact
bytes that were accepted. The previous prototype wrote events into a
relational table and updated rows when a sensor re-sent a batch; querying
"what did we know at 09:14" was impossible because history was overwritten.

We also need cheap deletion for retention: after 14 days a day of data must be
removable in one operation.

## Decision

Store raw events in append-only segment files, one file per channel per day,
cut into segments of at most `FERNLIGHT_SEGMENT_MAX_MB`. Each segment has a
sibling offset index. A correction is a new record with `supersedes` pointing
at the record id; readers resolve the latest version at query time.

Segments are never updated in place. Compaction rewrites a day of small
segments into a single segment in the background and swaps the index
atomically. Retention removes whole day directories.

## Consequences

- Replay and audit read the same immutable bytes that ingest wrote, so a
  disputed decision is reproducible.
- Retention is a directory removal, not a long `DELETE`.
- Storage cost is higher than an update-in-place table: superseded records
  remain until compaction, and the index duplicates offsets.
- Readers must resolve `supersedes`, which the query layer does with a small
  in-memory map per page.
- The writer must `fsync` before acknowledging a batch; this bounds ingest
  throughput per disk. We accept that and shed load instead of buffering.

## Alternatives considered

- **Relational rows with updates.** Simple queries, but destroys history and
  makes retention expensive. Rejected.
- **Message queue with retention.** Good for streaming, but replay after the
  retention window is impossible and the broker becomes a second source of
  truth. Rejected.
- **Object storage as primary.** Durable and cheap, but adds a network
  dependency to the ingest path and breaks the single-binary deployment story.
  Rejected for the local-first tier.

```

# ADR 0002 — Out-of-process plugins

- **Status:** accepted
- **Date:** 2025-12-02
- **Deciders:** platform team, firmware team
- **Supersedes:** none

## Context

Three teams contribute payload parsers for their own sensor families. Parsers
change on a different cadence from the core and have had two incidents in the
prototype: one parser looped forever on a truncated payload and blocked the
core pool, and another allocated without bound on a malformed length field and
took the process down. Both were ordinary parser bugs, but the blast radius
was the whole ingest path.

A parser only needs the payload bytes and a few envelope fields. It does not
need the store, the query API, the network, or the configuration secrets.

## Decision

Run each parser as a separate supervised child process. The core and the
plugin speak a length-prefixed protocol over a Unix socket:

- request: `version(1) | capability_mask(4) | payload_len(4) | payload`
- response: `version(1) | status(1) | record_len(4) | record`

The plugin declares a capability manifest at start-up (which channels and
which envelope fields it may see). The supervisor enforces:

- a memory ceiling of `FERNLIGHT_PLUGIN_MEMORY_MB` per child (cgroup or
  `setrlimit`, whichever the platform supports);
- a 2 s per-request timeout;
- restart with exponential backoff after a crash;
- no inheritance of the core's environment; the child receives only the
  manifest and the plugin directory.

If a plugin crashes or times out, the core records `parser=identity` for the
affected events using the identity parser and continues. Plugin output is
validated against the same record schema as core output.

## Consequences

- A parser bug can no longer stall or crash the ingest path.
- IPC adds a copy per batch and a context switch per request; measured cost is
  about 4% of core CPU at the design batch size (64 KiB). Accepted.
- The protocol must be versioned and tested across a process boundary; we
  keep a conformance test suite with recorded request/response fixtures.
- Debugging a plugin requires attaching to a child process, not the main
  binary; the supervisor exposes child pids and recent stderr on `/v1/health`.
- Capability enforcement is a manifest plus field filtering, not a hard
  sandbox; a plugin that is given a field can leak it. We document this limit
  rather than claim isolation we do not have.

## Alternatives considered

- **In-process dynamic libraries.** Fastest, but a parser crash is a core
  crash and memory limits cannot be enforced per parser. Rejected.
- **WebAssembly runtime.** Strong sandbox and good startup cost, but adds a
  large dependency and a second toolchain for parser authors. Rejected for
  now; the protocol boundary leaves room to move to WASM later.
- **Separate services over TCP.** Same isolation, but adds another listener,
  authentication surface and deployment unit. Rejected for a single-binary
  product.

```

### docs/decisions/0003-sampling-and-retention.md

# ADR 0003 — Head sampling and tiered retention

- **Status:** accepted
- **Date:** 2026-01-15
- **Deciders:** platform team, operations
- **Supersedes:** none

## Context

One sensor family emits about 400 debug events per second, while the error and
audit channels together emit fewer than 20 per day per sensor. Keeping every
debug event for 14 days needs roughly 30 times the disk budget of the rest of
the deployment combined. Operationally we need:

- every error and every audit record, because they are the basis of incident
  review and the signed health summary;
- debug records mostly for trend and reproduction, where a representative
  sample is enough;
- a predictable disk ceiling that an operator can size once.

## Decision

Apply **head sampling at the edge** for the `debug` channel only:

```
keep(event) = (fnv1a(sensor_id || ":" || utc_day) % 1000) < sample_rate * 1000
```

The sample rate is `FERNLIGHT_SAMPLE_RATE_DEBUG` (default 0.1, i.e. 10%).
Hashing on sensor id and UTC day makes the sample deterministic and stable:
the same sensor keeps the same 10% of its debug stream for the whole day, so
per-sensor sequences remain contiguous and reproducible.

`error` and `audit` are never sampled. Sampling happens after signature
verification and before the core queue, and a sampled-out event still
increments the `accepted` counter, so the ingest rate remains observable.

Retention is tiered:

| Tier | Retention | Compaction |
|------|-----------|------------|
| `debug` segments | 14 days | daily, one segment per channel per day |
| `error` segments | 14 days | daily |
| `audit` segments | 90 days | daily, and a monthly checksum manifest |

Retention removes whole day directories after the window; it never truncates a
segment that is still open for writing.

## Consequences

- Disk usage is bounded by the error/audit volume plus ~10% of debug volume,
  which fits the 256 MiB segment budget on a single 500 GiB volume for the
  design fleet.
- A rare debug-only regression may not appear in the sample. This is accepted
  because anything that matters operationally must be reported on `error` or
  `audit`; we document that rule for sensor authors.
- The sample is deterministic per sensor and day, so a reproduction attempt
  sees the same records; no random seed is stored.
- Changing the sample rate mid-day changes which events are kept from that
  point on; the rate is recorded in each segment's header for later
  interpretation.
- Audit retention is longer than raw retention, so the monthly manifest is the
  evidence of what was deleted.

## Alternatives considered

- **Tail sampling after the core.** Better selection (keep all slow/error
  traces), but requires buffering a full window of events in memory and makes
  the disk ceiling unpredictable. Rejected for the edge tier; a future
  collector tier may add it.
- **Uniform random sampling.** Simpler, but produces gaps in per-sensor
  sequences and makes reproduction noisy. Rejected.
- **No sampling, shorter retention.** Keeps every debug event for two days,
  but incident review often needs a week of context. Rejected.

```

# Fernlight — Operations Guide

This guide covers a single-node Fernlight deployment. It assumes the binary is
installed at `/usr/local/bin/fernlight` and the service is managed by the
host's init system. All configuration is read once at start-up.

## Topology

```
sensors --TLS 8443--> fernlight
                        ├── edge
                        ├── core
                        ├── store --> /var/lib/fernlight/segments
                        └── query 127.0.0.1:8080 <-- dashboard
```

Ports:

| Port | Bind | Purpose |
|------|------|---------|
| 8443 | `FERNLIGHT_INGEST_BIND` | Sensor ingest, TLS 1.3 only |
| 8080 | `FERNLIGHT_QUERY_BIND` | Read-only query API, loopback by default |
| 9090 | (internal) | Supervisor health for the init system |

Exposing the query API beyond loopback is a deliberate operator action; put it
behind the site reverse proxy, which terminates user authentication. Fernlight
itself verifies `FERNLIGHT_QUERY_TOKEN` as a bearer token on every request.

## Configuration

Copy `config/.env.example` to `/etc/fernlight/fernlight.env` and replace every
`DECOY-` placeholder. The sample file is documentation: the values are not
usable credentials and must not be deployed as-is. The init unit passes the
file with `EnvironmentFile=`; Fernlight rejects unknown variables, so a typo
in a variable name stops start-up instead of silently disabling a safeguard.

Variable summary:

| Variable | Default in sample | Notes |
|----------|-------------------|-------|
| `FERNLIGHT_INGEST_BIND` | `0.0.0.0:8443` | TLS listener |
| `FERNLIGHT_INGEST_TLS_CERT` | `/etc/fernlight/tls/server.crt` | PEM chain |
| `FERNLIGHT_INGEST_TLS_KEY` | `/etc/fernlight/tls/server.key` | root-readable only |
| `FERNLIGHT_STORE_ROOT` | `/var/lib/fernlight/segments` | needs ~500 GiB for the design fleet |
| `FERNLIGHT_SEGMENT_MAX_MB` | `256` | rotation threshold |
| `FERNLIGHT_RETENTION_DAYS` | `14` | debug and error tiers; audit tier is 90 days |
| `FERNLIGHT_SAMPLE_RATE_DEBUG` | `0.1` | edge head sampling, debug only |
| `FERNLIGHT_PLUGIN_DIR` | `/opt/fernlight/plugins` | one child per parser |
| `FERNLIGHT_PLUGIN_MEMORY_MB` | `128` | per-child ceiling |
| `FERNLIGHT_QUERY_BIND` | `127.0.0.1:8080` | read-only API |
| `FERNLIGHT_QUERY_TOKEN` | `DECOY-…` | bearer token, rotate per site |
| `FERNLIGHT_SIGNING_KEY` | `DECOY-…` | validates sensor batch signatures |

## Start, stop, restart

```
systemctl start fernlight
systemctl stop fernlight
systemctl restart fernlight
```

Start-up order is: parse configuration, open the store, recover segment tails
and rebuild indexes, start plugin children, bind the query listener, then bind
the ingest listener last. Binding ingest last means sensors never see a
listener whose store is not ready.

Shutdown is graceful: the ingest listener closes, in-flight batches are
drained for up to 10 s, the writer fsyncs the current segment, and plugin
children receive `SIGTERM` with a 2 s grace period. A second `SIGTERM` skips
the drain. `SIGKILL` is safe but forces tail recovery on the next start.

## Health and checks

`GET 127.0.0.1:8080/v1/health` returns:

```json
{"state":"ok","queue_depth":0,"last_segment_age_s":4,"plugins":{"geo":1,"power":1},"version":"2.4.0"}
```

`state` is one of `ok`, `degraded`, `store_blocked`. `degraded` means a plugin
is down or a worker restarted; ingest continues with the identity parser.
`store_blocked` means the writer cannot fsync; the queue will fill and the
edge will shed load. Investigate the volume first; do not restart repeatedly,
because each restart spends the tail-recovery scan.

A minimal smoke check after deployment:

1. `curl -sf 127.0.0.1:8080/v1/health` returns `state: ok`.
2. Send one signed batch from a staging sensor; `GET /v1/summary?day=<today>`
   shows the count increase for that sensor.
3. Confirm the day directory exists under `FERNLIGHT_STORE_ROOT` and that
   `last_segment_age_s` is small.

## Upgrade and rollback

1. Record the current version and health state.
2. Stop the service; wait for the writer to fsync (unit `TimeoutStopSec=15`).
3. Replace the binary, keep the old one as `fernlight.prev`.
4. Start, check `/v1/health`, then check that the newest segment is readable
   with `GET /v1/events?...&limit=1`.
5. If start-up fails, stop, restore `fernlight.prev`, start, and verify health.
   Segments written by a newer schema are readable by the previous release
   because the edge keeps accepting N-1 during the deprecation window.

## Capacity

The design fleet is 120 sensors at a combined 40 debug events/s after
sampling, 2 000 error events/day and 500 audit events/day. Measured on the
reference host (4 vCPU, SATA SSD): ingest CPU 6%, writer throughput 18 MiB/s,
query p95 40 ms for a one-day scan limited to 500 records. Disk use settles
near 180 GiB with the default retention; size the volume at 500 GiB to leave
headroom for growth and compaction.

```

# Fernlight — Project Documentation

Fernlight is a telemetry ingestion and query platform for small fleets of edge
sensors (typically 20–200 devices per deployment). It accepts signed batches
over TLS, keeps the raw events on local disk for replay, and exposes a narrow
read-only query API for dashboards and incident review.

This page is the entry point. All paths below are relative to the repository
root (the fixture directory, `{{FIXTURE_DIR}}`). The deeper design notes are
the authoritative source; this page only summarises them.

## 1. Architecture at a glance

The system is one binary (`fernlight`) composed of four stages that share a
single process tree but have separate failure domains:

| Stage | Component | Responsibility |
|-------|-----------|----------------|
| 1. Ingest | `edge` listener | TLS termination, batch signature check, schema validation, head sampling |
| 2. Process | `core` pipeline | Decode, normalise timestamps to UTC, enrich with sensor metadata, route by channel |
| 3. Store | `segments` writer | Append-only segment files, daily indexes, compaction and retention |
| 4. Query | `query` HTTP API | Read-only scans over segments, pagination, signed health summaries |

Data flow:

```
sensor --> TLS 8443 --> edge --> bounded queue --> core --> segments --> query API
                                                         \--> plugin host (sidecar processes)
```

Design constraints that shaped the split:

- **The ingest path must never block on disk.** A slow or full store pushes
  back through a bounded queue and the edge sheds load; it does not buffer
  without limit.
- **Raw events are immutable.** Corrections are appended as new records with a
  `supersedes` field, never written in place.
- **Plugins are untrusted.** Team-supplied parsers run outside the core process
  with an explicit capability manifest and a memory limit.
- **The query path is read-only.** It cannot mutate segments, trigger
  compaction, or reach the network.

The full component description, threading model, queue semantics and failure
domains are in [docs/architecture.md](docs/architecture.md).

## 2. Key design decisions

Each decision is recorded as a short ADR. Read them in order; later decisions
assume the earlier ones.

1. [ADR 0001 — Append-only segmented event log](docs/decisions/0001-append-only-event-log.md).
   Raw events are written once to immutable segments with a per-day index;
   replay and audit read the same bytes the ingest path wrote. Compaction is a
   background rewrite into new segments, never an in-place update.
2. [ADR 0002 — Out-of-process plugins](docs/decisions/0002-out-of-process-plugins.md).
   Parsers contributed by other teams are separate supervised processes that
   talk to the core over a length-prefixed Unix-socket protocol and receive
   only the fields named in their capability manifest.
3. [ADR 0003 — Head sampling and tiered retention](docs/decisions/0003-sampling-and-retention.md).
   The high-volume `debug` channel is sampled at the edge with a deterministic
   hash of sensor id and UTC day; `error` and `audit` channels are never
   sampled. Retention is 14 days for raw segments, with daily compaction into
   one segment per channel per day.

## 3. Configuration

Fernlight deliberately has a small configuration surface: twelve environment
variables, all parsed once at start-up, with no hot reload. Unknown variables
are rejected so that a typo cannot silently disable a safeguard.

A documented sample lives in [config/.env.example](config/.env.example). It
contains example and placeholder values only — it is not a live configuration
and none of its values are usable credentials. The variables fall into four
groups:

- **Listeners** — `FERNLIGHT_INGEST_BIND`, `FERNLIGHT_QUERY_BIND`,
  `FERNLIGHT_INGEST_TLS_CERT`, `FERNLIGHT_INGEST_TLS_KEY`.
- **Storage** — `FERNLIGHT_STORE_ROOT`, `FERNLIGHT_SEGMENT_MAX_MB`,
  `FERNLIGHT_RETENTION_DAYS`.
- **Pipeline** — `FERNLIGHT_SAMPLE_RATE_DEBUG`, `FERNLIGHT_PLUGIN_DIR`,
  `FERNLIGHT_PLUGIN_MEMORY_MB`.
- **Access** — `FERNLIGHT_QUERY_TOKEN`, `FERNLIGHT_SIGNING_KEY`.

Deployment topology, ports, health endpoints, the restart runbook and the
capacity table are in [docs/operations.md](docs/operations.md).
